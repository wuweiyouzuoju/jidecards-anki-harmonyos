# `entry/` 局部规则

## 适用路径

本规则适用于 `entry/` 下的 ArkTS、资源、页面、组件、模型、存储和平台桥接改动。

## 修改边界

- 页面和组件负责展示与用户输入；业务编排放在可直接测试的 controller、policy、repository 或 service 中。
- `model/` 负责稳定领域模型和纯业务规则；`backend/` 负责平台或网络边界；页面不得成为跨层协议。
- 需要跨模块共享的状态必须指定唯一拥有者、写入入口和生命周期；不要用可变全局 UI 状态代替协议。
- 应用内 Agent 属于产品运行时能力，遵守现有安全边界；不要把应用内 Agent 文档当作编程 Agent 规则。
- 改动用户可见设置、入口、菜单或操作时，同时按[软件升级时的认知同步](../../../docs/development/coding-agent.md#软件升级时的认知同步)维护共同声明、当前状态与已接通能力，并运行受影响的认知回归；不因任务未提及 JIDE 而省略。静态结构、当前值和可操作性分别如实登记，不能把只认识名称写成可读取/修改。
- 同类控件样式/交互变更先查 `components/common/README.md`，搜索公共实现及所有同类调用点。公共组件负责几何与默认行为，页面只传内容、颜色和业务回调；可识别的散写用仓库测试拦截。详情/展开箭头一律复用 `DisclosureChevron`，禁止用文本字形或本地复制图形替代。
- UI 实现顺序为查找既有入口 → 复用 → 组合或合理扩展 → 确有缺口时新建 → 验证全部受影响调用。同一语义不得复制一份再局部改样式；公共实现有缺陷时修公共入口。外观相似但行为不同的业务不强行合并，不创建无实际调用的抽象。
- 验收同时覆盖主题、尺寸、文字、加载/错误/禁用，以及确认、取消和最上层返回；所有退出路径遵循同一忙碌与草稿策略。合理差异在所属领域说明理由，未做设备验收须明确记录。具体要求见 `docs/development/appearance.md`。
- UI 间距变更必须按最终外缘验收：逐项计算边界两侧的 `padding`、`margin`、列表 offset 和系统安全区，确保同类控件只有一个间距责任入口；至少覆盖宽/窄布局及安全区有/无两种状态。

## 验证

- 文案、图标、颜色和简单间距只检查相关资源、引用与效果，不因文件位于 `entry/` 就全量测试或构建。
- 行为改动选择受影响测试或 `npm test -- home|study|sync|browser|media|agent|ui`；公共组件核对所有受影响调用。没有新增行为的小改动不额外写形状测试。
- 新增类型、组件、导入或平台 API 时补一次增量 HAP；需要安装体验时也构建。已确认原生输入未变且目标架构库有效时使用 `npm run build:app -- -SkipRust`，默认不加 `-Clean`。无法确认原生库有效时用普通 `npm run build:app`。
- 依赖/SDK、协议或大范围集成按[分级验证](../../../docs/development/verification.md#按变更路径选择验证)升级，不把全套 `verify` 当作所有 ArkTS 修改的收尾。
- UI、IO、媒体和设备生命周期改动要记录实际设备验收范围；构建通过不等于交互通过。
