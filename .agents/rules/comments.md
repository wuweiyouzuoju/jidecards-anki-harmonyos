# Comments 规则

## 三层注释模型

关键模块按需记录意图与不变量；简单函数不强制注释。以下只是有必要时的参考格式：

```typescript
/**
 * 一句话意图说明。
 *
 * 更详细的业务说明（可选，2-3 句话）。
 *
 * Invariants:
 * - 不变量 1（必须保持的隐式约束）
 * - 不变量 2
 *
 * Extension Points:
 * - 扩展点 1（如何在此处加新功能）
 * - 扩展点 2
 */
```

## 各字段语义

| 字段 | 必填 | 内容 |
|---|---|---|
| 意图说明 | 有注释时 | 一句话说清"这个函数做什么、为什么需要" |
| 业务说明 | 否 | 复杂逻辑补充：为什么选这种实现、踩过的坑、关键约束 |
| Invariants | 有隐式约束时 | 调用方必须保证的前提、函数保证的输出、不可破坏的隐式约束 |
| Extension Points | 存在非显然扩展约束时 | 如何在此处加新功能、参考实现指向 |

## 不要写

- ❌ 流水式改动历史（"2026-07-30 修改"）—— 用 Git 追溯；长期决策写入 `docs/decisions/`
- ❌ 复制整张调用图或易过期行号 —— 用 `rg` 和调用点定位；必要的稳定入口可链接到当前领域文档
- ❌ "What"（这行代码做什么）—— 代码自解释
- ❌ 完整重述代码逻辑 —— 只补充代码本身不能说明的意图与约束，不按行数判断价值
- ❌ 块 ID（`@块ID SETTINGS-RATEAPP-001`）—— 旧式 8 字段注释，不再新增

## 旧式 8 字段注释（迁移状态）

项目历史上使用过 `@块ID / @名称 / @作用 / @输入 / @输出 / @业务规则 / @副作用` 等字段注释：
- 既有格式不批量改写；内容过期时必须随实现修正，不能以保留格式为由保留错误说明
- 新增注释按需记录意图、不变量和扩展约束，简单函数不强制套模板
- 不再新增 @块ID

## 行内注释

- 写"为什么这么写"，不写"改了什么历史"
- 保持精简（1 行优先，不超过 3 行）
- 长期复杂决策走 `docs/decisions/`，源码注释保持精简

## 资源引用注释

动态拼接 i18n key 且映射规则不明显时，在调用点附近解释约束；静态 key 不重复注释：

```typescript
// i18n key 与 ColorTheme 联合类型一一对应：theme_color_aurora / forest / midnight / lagoon / sunset / lemon。
return this.getUIContext().getHostContext()!.resourceManager.getStringByNameSync('theme_color_' + theme);
```
