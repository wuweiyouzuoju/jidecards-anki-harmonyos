# 编程 Agent

[返回任务索引](../../PROJECT_CONTEXT.md)

本页只约束负责修改 jidecards 仓库的编程 Agent。产品运行时的应用内 Agent 见 [应用内 Agent](agent.md)。

Agent-first 优先级与开发流程统一见根 [AGENTS.md](../../AGENTS.md)。本页补充协作、同类问题的发现方法与重构边界；任务验收见 [开发任务契约](task-contract.md)。

## 多 Agent 协作

1. **先定归属。** 在任务说明中简短列出负责范围、共享接口负责人和依赖就绪条件。公共文件/接口指定一个写入负责人；调用方按约定契约开发，不各自猜实现，不强制另建协调文档。
2. **避免同处并写。** 同一文件的重叠修改交给负责人串行处理；确需独立并行时用隔离 worktree，再由指定集成人合并。worktree 不自带其他任务的未提交依赖，依赖交接后再验证。
3. **失败先归因。** 根据日志、diff 和调用关系区分本任务、其他任务、环境/缓存或原因未明；不能只凭文件名甩锅。本任务引起的跨文件问题由本任务修复，涉及他人正在编辑的部分先协调。其他任务未就绪则记录文件、错误及依赖，继续独立工作，交由负责人处理或明确移交责任后接手。
4. **禁止代补过关。** 不得为凑编译/测试通过，在生产代码中补对方职责的占位、空返回、假成功、吞错或删调用；也不得弱化断言、扩大 mock、改基线或回滚对方改动来掩盖失败。测试替身只在测试隔离边界使用，不算真实集成已完成。接手后实现完整约定行为，再验证。
5. **保留他人现场。** 修改前查看工作树，写共享文件前重读最新内容，局部补丁保留他人修改；未明确授权不得 stash、reset/restore、切分支、清理共享目录或终止他人进程。提交/回滚仅包含本任务变更，无法区分的同文件改动先协调。
6. **分开局部与联合验收。** 各任务只报告自己的实际验证范围；源码尚在变化时，全库失败不能冒充本任务失败或联合通过。共享构建、清缓存和依赖安装串行或使用独立目录，不绕过构建锁；依赖就绪且工作树稳定后，由指定集成人验收一次。日志/交付产物用任务独立路径，避免后续构建覆盖证据。

开源参考：[OpenClaw 的责任与共享工作区约定](https://github.com/openclaw/openclaw/blob/main/AGENTS.md)、[失败归因与不掩盖失败](https://github.com/openclaw/openclaw/blob/main/.agents/skills/openclaw-testing/SKILL.md#test-failure-policy)、[Qualcomm 的多 Agent 工作区保护](https://github.com/qualcomm/AI-Harness/blob/main/AGENTS.md#collaboration--safety-notes)、[Git worktree 隔离](https://git-scm.com/docs/git-worktree)。以上为参考，执行规则以本节为准。

## 软件升级时的认知同步

这是所有相关开发任务的完成条件，见根 `AGENTS.md`、`entry/` 局部规则与[开发任务契约](task-contract.md)。编程 Agent 负责在实现功能时完成接入，用户无需逐次提醒；JIDE 在更新后的运行中从当前代码与真实工具生成认知，不要求另外培训、补写长期记忆或清空旧会话。当前机制自动同步已登记的语义，不扫描任意 ArkUI 源码或像素来推断全部新功能。

以新增设置选项为例，开发按下列责任入口完成：

1. **结构与名称**：在 `SettingsStructure.SETTINGS_GROUPS` 登记稳定 ID、所属分组、资源键及显隐条件，UI 用 `settingsItemText` / 共同分组渲染；新增分组同时维护 `SettingsNavigation` 与原设置面板。`get_app_structure` 自动包含新项，改名、模式变化和删除也跟随同一来源。说明用途时复用真实配置描述/帮助来源；不能仅从名称编造效果。
2. **当前状态**：需要 JIDE 读取当前值时，接入 `AgentSettingsTools` 与 `AgentPreferenceSettings` / 实际读取器，复用原设置存储；界面自身的加载、选中、禁用和条件状态由原拥有者发布 `AppInterface` 观察。只登记结构的项可以被定位，当前值尚不可读时不能虚报值。
3. **操作能力**：确需 JIDE 操作时，接通已有领域入口、严格 Schema、真实 Registry 和原确认/执行规则；仅新增设置 UI 不自动开放修改权限。动作目录只声明实际接通能力，移除功能同时移除其声明、能力及观察。
4. **验证与交付**：直接运行共享标签和结构工具，覆盖新项的名称/位置、显隐、已接通读取/操作与不可用边界；改名/移除不能留下旧绑定。相关领域回归与平台检查仍按改动性质选择，交付明确认知同步范围，未登记的旧 UI 不能冒充自动覆盖。

`ai-agent-app-structure.test.mjs` 自动扫描整个 `components/settings/` 树，核对共同声明、资源和静态 `settingsItemText` 绑定，新增组件也纳入；未知 ID、资源缺失、声明缺少 UI 引用和分组分支缺失会失败。新增/改名/显隐/移除的行为回归直接执行真实共享标签与结构生成，验证新能力不需要另改 JIDE 目录。`npm run impact` 对设置组件与共同认知契约安排 Agent 领域回归，完整仓库检查也包含这些测试。

这些门禁能检查可识别的登记关系，不能证明任意手写 `Text`/`Button` 或动态表达式都已登记；编程 Agent 仍须查全本任务 UI 和实际回调，按上述规范接入。这是“开发默认负责、运行自动同步”的保障，没有承诺 JIDE 无需开发接入便能自动理解任何新界面。

## 同类变更闭环

一次反馈提供的是问题入口，不能自动视作全部影响范围。编程 Agent 应主动检查同类实现，让下一次修改能从明确入口完成，并让可检测的遗漏在验证时失败。这条原则适用于 UI、交互、文案、配置、协议适配和错误处理。

1. **按语义查全。** 修改前搜索组件/函数名、资源键、可见文字或符号、旧写法和替代实现，再沿调用点确认实际使用位置。不能只搜索已经复用公共入口的代码，否则会漏掉散写副本。检查同一行为在不同页面、设备形态和状态下的入口。
2. **确定责任和差异。** 同一语义、同一变化原因的实现由一个明确模块负责；调用方只传必要内容、配置和业务回调。外观相似但业务含义不同的代码不强行合并。需要保留的差异在所属领域文档说明理由，不靠无解释的例外列表。
3. **让代码真正复用。** 优先修改既有公共实现，并迁移本次范围内的同类副本。若不存在公共入口，按已有重复提取最小组件、函数或策略。注释和索引只能指路，不能代替真实调用；不建立无调用方的抽象或集中管理所有业务的万能模块。
4. **用检查防止回退。** 为行为建立真实执行的回归；对可机械识别的散写、依赖方向和资源重复增加全仓扫描，新增文件也应自动纳入。检查应能抓住原故障或旧写法，不只断言文档里出现了某句话。静态几何和构建检查不能冒充设备视觉验证。
   对 UI 几何变更，必须先列出每个目标边界两侧的全部贡献项（父/子 `padding`、`margin`、列表 offset、固定操作区 inset 和安全区），计算最终外缘距离；同一语义间距只能有一个责任入口。宽/窄密度、无/有系统安全区和 loading/done 等状态都要分别核对，不能只检查某个局部属性值。
5. **让下一位 Agent 找得到。** 根入口链接当前领域说明；领域说明指向唯一实现、调用查找方法和验证命令；公共代码边界用简短注释记录容易误改的不变量及原因。索引以代码符号和搜索方法定位调用方，避免手工维护另一份容易过期的完整文件清单。
6. **交付覆盖证据。** 说明查了哪些同类入口、哪些已统一、哪些差异有意保留、验证如何覆盖原故障，以及未验证部分。重复出现同类漏改时，除了修功能，还应补足发现入口、公共边界或检查中的缺口。

例如详情/展开箭头偏位，应查所有文字箭头和已有图标入口，统一绘制几何、保留所在行的点击与主题语义，再用扫描防止重新散写。对媒体或同步错误的修复，同样先定位真正拥有状态的模块，不能仅让几个页面显示一致却继续各自维护冲突状态。模块入口见 [责任表](ownership.md)，验收要求见 [任务契约](task-contract.md)。

范围仍以用户目标为边界：查全不等于顺手重写全项目；无关发现可以记录，但不扩展为未请求的产品行为。决策依据见 [同类变更的发现、复用与验证](../decisions/2026-09-26-consistent-change-coverage.md)。

## 名称边界

- 编程 Agent：负责阅读、修改、测试和交付本仓库的开发 Agent。
- 应用内 Agent：jidecards 运行时提供的 AI 制卡/改卡功能。
- 文档中单独写“Agent”时，必须根据上下文明确属于哪一种；任务入口、测试名和决策记录优先使用完整名称。

## 不得降低的能力

- 不得为了局部功能牺牲 Agent 可定位的模块边界、可测试业务规则或验证入口。
- 不得把关键规则只写进源码旁注、聊天记录、被忽略目录或历史计划。
- 不得用历史测试数量、旧版本说明或未完成 checkbox 代替当前源码和实际验证。
- 不得让新增复杂度没有责任表、验证命令或交接信息。
- 不得把统一规范只落实在文档或局部修补中；同类实现应有可查找的责任入口和覆盖遗漏的验证路径。


## 重构前的行为约束

先从当前领域文档、调用点和现有测试写出本次必须保留的用户交互，再命名状态所有者和需要移动的决策。例如媒体报告的连续滑动属于交互约束，跨桥分页属于传输实现；二者不能混为 UI 翻页。声明式布局、样式及组件接线较长不自动构成拆分理由。

沿用本地 architect/refactoring-guru 工作法：先移动状态和依赖它的决策，再保留薄的页面适配。禁止仅减少行数、复制一组共享状态到 Controller、增加无调用方的通用层。替换源码位置断言之前，先建立真实模块行为回归。知识按任务路由按需加载，事实只保留一个来源；依据与取舍见 [2026-09-26 治理决策](../decisions/2026-09-26-agent-first-boundaries.md)。
