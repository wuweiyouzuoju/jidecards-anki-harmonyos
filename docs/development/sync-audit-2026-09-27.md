## 为什么卡片数据同步需要等待

锁定的 Anki Core 在 `sync_collection_inner()` 中通过 `with_col()` 执行整个 `normal_sync()`，包含网络等待，而非仅在最后写数据库时占用集合。jidecards 原生 `BackendRegistry.call()` 也把同一后端的普通 RPC 串行化；AbortSync 有专门的绕锁通道。

因此，当前引擎同步期间不能任意取卡、评分、编辑或替换集合。取消必须等原请求回滚或提交完成；设置一个前端“已取消”状态不代表可以立即读写数据库。已经确认的全量替换需要更严格地保护集合重新打开过程。

媒体线程只在取得媒体管理器和进度句柄时短暂访问集合，网络传输使用独立的媒体流程。媒体传输通常不要求停止学习，但当前 UI 和刷新编排仍可能额外阻挡入口。媒体尚未下载时，对应图片或音频也可能暂时不可用。

证据：`native/rsharmony/src/lib.rs` 的 `BackendRegistry.call()`；`third_party/anki/rslib/src/backend/sync.rs` 的 `sync_collection_inner()`、`full_sync_inner()`、`sync_media_blocking()`。

## 已确认的问题

### P1：其他页面会消费媒体错误，导致同步面板误报成功

- 入口：[媒体管理面板](../../entry/src/main/ets/components/settings/媒体管理面板.ets) 的 `检查媒体同步状态()`、维护会话的 `isSyncing()`，以及[首页](../../entry/src/main/ets/pages/首页.ets) 的牌组媒体清理适配器，都直接调用 `媒体同步状态()`。
- Core 的 `get_media_sync_status()` 对完成任务执行 `task.take().join()`，错误只交给第一次读取者；后续读取没有任务，返回 `active=false`。这不是可供多个消费者随意轮询的只读状态接口。
- 如果媒体任务失败后，媒体管理页先读取，页面的 catch 将其处理为“媒体没有在同步”；随后同步面板读到 `active=false`，提示同步成功并清除媒体待同步标志。
- 已用实际 ArkTS 方法配合遵循 Core 一次性消费语义的后端替身复现上述顺序；未声称已在真实网络上稳定触发该竞态。
- 修复方向：媒体任务结果由唯一拥有者读取、保存并发布；其他页面读取共享快照，不直接消费底层终态。清理操作仍须有真正的媒体互斥，不能只改警告文案。

### P2：集合和 UI 都启动媒体任务，快速完成时会重复执行

- [同步面板](../../entry/src/main/ets/components/同步面板.ets) 的 `runSync()` 传入 `syncMedia=true`，Core 已自动启动媒体；随后 `启动媒体阶段()` 又调用 `同步媒体()`。
- 全量同步传入非空 `serverUsn` 时也会由 Core 启动媒体，然后 UI 再启动一次。冲突重检调用 `syncMedia=false`，则确实需要显式启动，不能把所有后续调用直接删掉。
- Core `sync_media_in_background()` 仅在旧任务仍运行时忽略重复请求；旧任务已完成则直接丢弃句柄并重新启动，没有消费旧结果。可能发生多一次扫描/联网，也可能丢失第一次失败。
- 已执行实际面板方法，模拟首个媒体任务在第二次 RPC 前结束，确认触发两次启动并丢弃首个结果。
- 修复方向：明确一个启动拥有者，覆盖增量、无变化、全量和冲突重检四条路径；验证失败结果和服务端媒体 USN 的处理，不依赖“重复启动安全”的注释。

### P2：集合已释放，学习仍等待首页统计和桌面卡片推送

- [HomeSyncController](../../entry/src/main/ets/model/HomeSyncController.ts) 的 `collectionFinished()` 设置 `refreshing=true`，`defer()` 将它和集合同步占用一起阻挡学习。
- 首页的 `refreshAfterCollection()` 等待完整主页加载。[HomeDataRepository](../../entry/src/main/ets/backend/HomeDataRepository.ets) 在返回快照前等待图表统计、偏好读取、`保存卡片数据()`；后者还顺序等待各张桌面卡片的 `formProvider.updateForm()`。
- 已串联执行实际 repository 和 controller 方法：集合 busy 已为 false，仅挂起桌面卡片保存，就能让“开始学习”继续排队；放行保存后才导航。
- 修复方向：必要的牌组存在性、选择和集合代次校验完成后放行学习；统计和桌面卡片更新由可持续完成的刷新任务负责。不能用未经持有的 fire-and-forget 替代，以免应用切后台后桌面卡片一直陈旧。

### P2：页面导航的保护范围比数据库访问更宽

- [首页](../../entry/src/main/ets/pages/首页.ets) 的 `openSettings()`、`openAISettings()` 在导航前就调用统一的 `deferForSync()`。
- 因而网络慢时，用户连设置页面都不能先进入。设置确有加载牌组等数据库行为，但主题和一般页面展示不必随数据库查询一起被挡在入口外。提醒页依赖集合，不能直接归为完全独立的页面。
- 当前统计页已经采用“先进入并展示快照，真正的数据库查询再等待”的方式，可作为局部设计参考。
- 修复方向：按页面内操作保护数据库访问；先显示独立内容，禁用或延迟依赖集合的操作。不能简单删除导航守卫而放任页面写数据库。

### P2：用户看不到“卡片已同步、仅媒体失败”的完整结果

- `notifyCollectionResult()` 只通知首页刷新；成功 Toast 在全部媒体结束后发出。同步详情主行一直使用通用的“同步中”，直到媒体轮询才追加媒体进度。
- `处理同步错误()` 把集合阶段与媒体阶段的错误合并成同一类网络错误文案，并清空媒体进度；卡片已经提交这一事实没有保留在错误展示中。
- 因此媒体超时可能被理解成卡片也没同步成功，引发反复点击。手动重试又从集合同步开始，进一步增加等待。
- 修复方向：明确展示“卡片数据已同步，可以学习”“媒体仍在同步/媒体同步失败”；详细错误保留阶段与可重试信息。是否提供只重试媒体，需要与唯一任务拥有者一起设计，不能另建并发入口。

## 已核查的保护与限制

- 老用户自动同步偏好迁移到新版键，旧开启记录不会自动延续；新版本显式开启才生效。
- 手动和自动请求共用租约；媒体阶段不占用集合，但账号和服务器修改仍等待任务结束。
- 学习优先请求会中止普通增量同步；取消信号绕过原生同步锁，等待原始调用结束后才放行。已有真实 Core 慢网络取消测试证明集合能够再次读取。
- 冲突方向由用户确认，执行前重新检查方向、端点和媒体 USN；未确认冲突不占用集合。全量替换期间不由学习自动中断。
- 面板隐藏与任务销毁不同；销毁过程等待已接受调用和媒体退出。媒体轮询避免重复并发，但这不能防止其他页面消费结果。
- 当前后台能力是短时收尾申请，不是持久下载服务，不保证系统挂起或结束进程后仍持续同步。
- 网络鉴权未配置 IO 超时时，锁定 Core 使用 30 秒默认值；它不是整个同步任务的总时限。此前模拟器连接超时不能仅凭这些实现缺陷归因，也不能靠调大超时判定修复。

## 同日修复

对照 Anki 26.05 的 [sync.py](https://github.com/ankitects/anki/blob/26.05/qt/aqt/sync.py) 和 [mediasync.py](https://github.com/ankitects/anki/blob/26.05/qt/aqt/mediasync.py)：集合/全量调用负责启动媒体，`start_monitoring()` 仅监测；完成集合即可恢复主要界面。对照本机 AnkiDroid `Sync.kt` 与 `worker/SyncMediaWorker.kt`：普通同步传 `syncMedia=false`，结束后显示卡片完成/媒体后台提示，独立 Worker 启动并监测媒体。问题在于原实现混用了 Core 自动启动与 UI 再启动，同时误把有消费副作用的接口当作一般查询。

修复沿用 Anki 桌面端的 Core 自动启动方式，避免丢失媒体 USN 的优化；只有不启动媒体的冲突重检成功分支显式启动一次。非拥有者改查租约，不读取 Core 终态。按用户最终选择，卡片完成与媒体完成分别使用“卡片数据已同步，可以开始学习”和“媒体同步完成”，每阶段去重，避免两条泛称“同步完成”。媒体错误展示保留卡片成功状态。失败重试继续走已有同步调度器，不引入第二套媒体任务。

首页必要牌组快照与统计/桌面卡片推送改为两个独立串行队列，保留推送完成责任和过期代次保护。设置整体导航放行，数据库相关分组及操作单独保护。新增 `sync-media-ownership.test.mjs` 和 `home-sync-refresh-runtime.test.mjs`，原有终态、重定向、销毁和图表测试迁移到真实的新责任边界；最初新增媒体回归在旧实现上有 8 项失败，修复后通过。

这些修改不改变 Core 的同步协议、调度算法或事务语义，也不代表模拟器网络超时的外部原因已经消失。构建和设备验收以本次修复交付记录为准。
