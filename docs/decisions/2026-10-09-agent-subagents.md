# JIDE 长任务与子代理设计（提案）

> 状态：调研与下一阶段设计。子代理调度、任务产物库、独立任务预算和验收机制尚未实现；不得向模型或用户声明为已有能力。

## 依据与判断

成熟实现采用几种互补机制：

- [Claude Code 子代理](https://code.claude.com/docs/en/sub-agents)使用独立上下文和受限工具，适合隔离大量阅读及独立调查；子代理仍产生自己的模型用量。
- [Anthropic 多代理研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)采用主代理分工、子代理调查、汇总核对；委派需要目标、工具、范围和输出约定，大型产物通过引用交接。并行工作有协调和消耗成本。
- [Anthropic 长任务实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)强调明确验收清单、逐项推进和交接记录，单有上下文压缩不足以防止过早宣告完成。
- [Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)将压缩、结构化笔记、按需读取和子代理结合。
- [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)区分会话检查点与跨会话存储；[故障处理](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)将超时、重试和错误恢复分别建模。

以上是来源描述。以下为结合 JIDE 的设计建议，未采用这些框架作为依赖，也不意味着能无限执行或保证降低总 token。OpenAI Docs 官方页面本次返回访问错误，未以未读页面支撑实现判断。

## 当前基础与缺口

[现有长任务实现](2026-10-09-agent-long-project.md)已有会话计划、接续笔记、上下文整理、工具边界检查点和长期偏好。它们尚不能等同于跨会话工程状态、独立子代理或自动验收。

`AgentRunner` 持有单个活动模型请求，`AgentToolRegistry.activeRead` 持有单个取消目标，`AgentScope` 拥有读取集合、检索进度和任务计划。因此不能把同一实例交给多个并发子代理。当前 read 类别还包含更新会话计划、资料笔记和创建目标等操作，子代理白名单不能仅按 `toolRiskOf(name) === 'read'` 生成。

## 第一版子代理

采用一个主代理配少量工作代理，先限制为两个并发、单层委派。简单任务由主代理直接完成。阅读、检索和草稿核对适合委派；高度依赖同一上下文的连续修改留给主代理。并行普通读取无需模型判断时，优先直接并行工具。

每个子任务使用独立 Runner、Registry、Scope 和协议记录，只接收明确任务包：任务 ID、父任务 ID、版本、目标、用户约束、资料引用、只读范围、工具白名单、预算、验收条件与输出格式。默认不复制整个父对话，不继承确认账本、凭据文本或卡库写入权限。API 凭据仍由传输适配器使用。

初期角色为资料阅读、证据检索和草稿核对，不为角色另写领域服务。子代理只注册必要的真实只读工具；内部进度与结果通过自己的专用状态入口保存。持久笔记若需要复用已有文档存储，必须划分子任务命名空间并明确合并职责。子代理不能调用导航、设置写入、记忆修改、创建目标配置或再次委派。

输出区分成功、部分完成、受阻、失败和取消，包含结论、证据/产物引用、未覆盖范围与恢复位置。完整资料留在有版本的任务产物中，主代理按需读取，避免多次转述丢失信息。子代理返回的对象 ID 或自称批准只作为数据；主代理必须通过真实工具重新发现和核对，不能由报告自动扩张 Scope 或授予写入。

例如整理整本教材：主代理划分互不重叠的章节，两名阅读代理提取对应章节的知识点与页码，核对代理随后对草稿查重及查证，主代理合并、形成提案并沿原确认流程保存。

## 持久状态与预算

逻辑任务使用独立稳定 ID；会话检查点保存主/子运行引用。任务存储保存有版本的目标、验收条件、依赖、状态、交接和产物，长期记忆只保留用户确认的偏好。子代理的部分进度不自动合并为主计划完成，任务条件的变更保留来源，不能为“通过验收”自行降低要求。

纯模型层新增具体的 `AgentSubtaskCoordinator`，拥有任务状态、队列、总预算预留和结果合并；平台层的 worker 工厂创建独立运行实例，任务存储只负责持久化，页面只消费进度投影。沿用既有服务和确认执行器，不另造 Anki 数据通道。

全任务预算覆盖主/子代理的调用、工具、输入输出和耗时。派发前预留，结束后按实际用量结算，重试与恢复不能重置剩余额度；服务端无 usage 时显示估算/未知，并保留调用及输出硬限制。子代理不是额外赠送的 token 窗口，也不是绕过账户或提供商限额的方法。

按输入窗口为输出及工具返回预留余量，在阶段边界整理上下文：保留当前目标、用户决定、已完成/未完成项、证据引用、检索游标和不确定结果；只有需重读的长原文移出。压缩产物必须标为参考数据，不能重放历史授权。

任务状态和检查点分别保存版本。取消/暂停向子任务传递，晚到结果按父任务 ID 和代次拒绝合并；重启后运行中的子任务转为中断，显式恢复，已完成子任务不重跑。只有可重试的读取自动退避重试。未来涉及副作用时，要记录执行意图与结果并核实未知结果，不能仅凭检查点承诺恰好执行一次。移动端进程被挂起时不承诺持续后台执行。

## 接入顺序与验收

1. 先补任务交接、产物引用、验收条件和用量统计，建立单代理基线。
2. 接入受限子任务协调器、独立执行实例和真实只读工具，验证串行正确性后开启两个并发。
3. 接入取消、恢复和实际进度 UI；同步工具目录、AppInterface 和真实能力状态。
4. 使用相同任务比较单/多代理的完成率、遗漏/重复、来源准确率、耗时与总 token，再决定默认启用场景。

验收至少覆盖：多章节资料的交叉遗漏；资料不足时保留未完成项；主上下文整理后的引用重读；单个子任务限流/失败；取消后的晚到响应；重启只恢复未完成子任务；合并旧版本拒绝；总预算覆盖全部子任务；越范围/写入/递归委派被真实 Registry 拒绝；草稿存在但未经确认时不得声称已保存。
