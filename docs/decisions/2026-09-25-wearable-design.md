# 手表端设计计划与官方依据

状态：设计提案，尚未实现或完成设备兼容验收。调研日期：2026-09-25。

[返回决策索引](README.md) · [任务入口](../../PROJECT_CONTEXT.md)

## 1. 目标与已确定的产品范围

尽量覆盖支持应用安装及必要通信能力的华为成人 WATCH、GT、FIT 系列，包括系统标注 HarmonyOS 5.0 的候选设备。系统营销版本不能直接作为 SDK/API 等价关系；是否支持以型号、地区、固件、开发模型及真机结果共同判定。

手表定位为手机协同复习端：牌组选择、题目、翻面、忘记/记得两档评分、提交状态和本次完成摘要。采用固定深色背景、系统字体；不包含应用好评、自定义背景、主题商城、赞助、AI、制卡编辑器及完整统计。

用户所说“5.0”是系统兼容版本，不是 5 MB 包体积要求；本计划不设未经用户要求的硬性 5 MB 指标。记录正式 HAP、安装占用、媒体缓存、内存和耗电，分别评估。

首版手机沿用现有 jidecards。其最低版本以 [build-profile.json5](../../build-profile.json5) 为准，不随手表适配自动下调。Android/iOS 伴侣、完全脱离手机的 Anki 调度、儿童表专项发布不在本次首版闭环内。

## 3. 平台选型与兼容矩阵

优先验证 JS/FA 基础客户端是否可通过平台适配和独立产物覆盖轻量穿戴及支持该模型的智能穿戴。若目标设备通信、显示或发布条件不满足，再增加 ArkTS/Stage 智能穿戴客户端。先验证复用范围，再决定是否引入第二套完整 UI。

| 路线 | 首阶段任务 | 可以承诺的范围 |
| --- | --- | --- |
| JS/FA 基础路线 | 轻量设备与智能设备分别安装最小应用，验证消息、持久化、文本、图片、前后台 | 通过验证的型号/固件组合 |
| ArkTS/Stage 路线 | API 18 起的候选基线审计；按接口核对设备行为差异 | 真机通过的智能穿戴；不得直接继承手机 API 21 并声称支持 18 |
| 系统显示 5.0 或更早的设备 | 确认旧 SDK、模型、通信接口、签名及分发渠道仍可用 | 验证前标记“待核验”，不能统一映射 API 12 |
| 不支持安装或应用间通信 | 记录不满足条件 | 不列入复习客户端兼容表 |

矩阵每行至少记录：型号、销售地区、完整固件版本、配对手机系统、应用运行模型、SDK、消息/文件能力、持久化、屏幕形状、表冠、安装结果、锁屏通信、复习写入与恢复结果。WATCH/GT/FIT 名称只用来收集候选，不作为平台判断。

发布产物、AppID 与包身份在平台选型后按官方分发要求落实。保留手机现有包名和签名；独立 HAP 不等于必然共用同一个商店 AppID。成人表与儿童表不能未经核对共用分发结论。

## 4. 用户流程与界面

1. 手机“手表复习”入口：授权、选择设备、检测应用、查看连接和兼容状态、开始/结束会话。
2. 手表首页：连接状态、今日剩余快照、继续学习和牌组入口。离线计数标明为上次同步结果。
3. 牌组页：最近/收藏牌组的简短列表，按需读取；不传完整大型牌组树和全部卡库。
4. 学习页：题目 → 显示答案 → 忘记/记得 → 提交中 → 下一张。加载及提交时阻止重复评分；答案前不显示评分。
5. 完成页：本次已确认的复习次数与耗时。次数只统计手机确认成功的操作。

交互采用触控全覆盖，表冠滚动作为增强，系统返回保持系统语义。圆屏留安全边距，方屏单独适配；以设备逻辑尺寸布局，不把像素尺寸当作 vp。两档按钮必须同时可发现且有文字标签；不依赖颜色、滑动方向或长按猜测评分。

状态至少区分未连接、连接中、加载、题目、答案、提交中、提交待确认、内容不支持和完成。返回/熄屏不会撤回已接受的手机写入。首版不依赖常亮、后台轮询或保活技巧；手机应用被回收时显示恢复指引。

## 5. 责任边界及候选目录

下列名称均为拟新增设计，不代表现有实现；选型通过后才创建模块及更新实际领域责任表。

| 位置 | 单一职责 |
| --- | --- |
| `wearable/`（采用 ArkTS 时） | 手表 HAP、导航、设备适配及展示 |
| `wearable-lite/`（JS/FA 工程） | 轻量基础客户端；必要时形成多个平台产物 |
| `shared/wear-protocol/` | 平台无关的协议 Schema、版本、序列化约束与跨运行时测试向量；不预设可直接复用 ArkTS 构建产物 |
| `entry/src/main/ets/model/wear/` | 手机学习会话、操作账本接口、能力协商、并发及恢复策略 |
| `entry/src/main/ets/backend/wear/` | Wear Engine、设备授权、文件及持久化适配；对接现有学习后端 |

复用入口：[StudySessionController](../../entry/src/main/ets/model/StudySessionController.ts)、[评分协议](../../entry/src/main/ets/proto/messages/SchedulerMessages.ts)、[学习与媒体说明](../development/study-media.md)、[同步领域](../development/sync-data.md)。

手机 Anki 集合是唯一权威状态；手表只有内容缓存与尚未确认的操作。手机保存原始 SchedulingStates，手表只发送语义评分；不发送任意后端方法号或可执行指令，不修改锁定的 Anki 协议。平台 Kit 不进入纯模型，页面不拥有已接受写入。

## 6. 通信协议与同步

首版是会话同步，不是两个完整数据库合并，也不把 APKG 导入导出当进度同步。

握手交换协议版本、应用版本、渲染能力、有效消息/文件上限。手机选择具体连接设备并校验应用身份；同时只允许一个手表复习写入会话。

拟定命令：`hello`、`listDecks`、`startSession`、`getCard`、`answer`、`queryOperation`、`endSession`。响应明确区分成功、状态过期、内容不支持、忙碌、协议不兼容和提交结果未知。

每条消息有协议版本、请求 ID、会话 ID、会话代次、类型及有效载荷。跨设备的集合/卡片/牌组 ID 用字符串编码，避免不同运行时的整数精度差异。手表评分使用字符串 `again` / `good`；手机映射项目既有常量，不将界面按钮编号误当后端枚举。

内容包包含卡片 ID、题面令牌、正反面、资源清单和摘要。短控制消息走消息通道；大题面与媒体走文件，缓存命中时只传资源标识。接收临时文件后检查长度、哈希及安全文件名，再原子替换为已完成资源。协议上限是本产品上限与设备上限的较小值；禁止把任意媒体路径拼入沙箱读取。

预取最多用于减少内容展示等待；每次评分后的下一张由手机 Anki 队列重新决定，手表不能把预取顺序当作权威队列。耗时按活跃答题时间计算，排除断线及后台等待；手机保存权威提交时间，处理时钟差异。

### 评分一致性

手表先持久化操作 ID 和评分意图，再发送；同一意图重试沿用 ID。手机在集合排他操作边界内校验会话代次、题面令牌、卡片及调度基线，使用现有 StudySessionController 提交，完成后保存结果并确认。手表收到确认才进入下一张。

手机学习、编辑、导入、同步等可能改变状态的入口必须与手表会话协调；仅已有 SyncActivity 等待并不足以证明两端评分互斥。发生其他变更时使远端题面失效，结束或重建会话。服务层串行化与生命周期规则需要直接测试，不能只禁用 UI 按钮。

操作账本状态拟定 `received` / `applying` / `committed` / `rejected` / `uncertain`。账本和 Anki 写入不天然处于一个事务，不能声称请求 ID 已实现崩溃情况下的严格恰好一次。P2 必须验证“Core 成功、结果持久化前崩溃”的窗口：优先调查现有后端能否提供足够的权威前后状态/复习记录进行核实；不能可靠证明时保留 `uncertain`，停止自动重放和新评分，引导在手机核实。不能通过直接改 SQLite、修改锁定协议或盲目补写评分消除不确定性。

断线后可以查看已完整缓存的当前题面；已有评分保留为待确认，不宣称已同步，也不继续离线推进整个队列。真正离线调度另行设计，不把延迟批量评分回放伪装成完整 Anki 离线学习。

## 7. 卡片兼容策略

手机复用 Anki 渲染结果，不将原始字段机械地当作问答。基础客户端使用受控的文本/换行/强调/图片块表示；需要严格识别支持的静态子集。不能通过正则剥除 HTML 后默认标记为可复习，因为隐藏文本、布局、脚本和条件模板可能改变题意。

| 内容 | 首版策略 |
| --- | --- |
| 简单问答、可正确转换的完形填空 | 用真实渲染结果制作协议夹具，逐张比对正反面 |
| 长文本 | 滚动或分页；不截断后仍允许评分 |
| 基础图片 | 根据尺寸生成展示资源，保持足够辨认能力；不可读则转手机 |
| 自定义 CSS/JS、复杂表格、公式、图片遮罩、拼写 | 分能力验证；未通过时明确转手机完成 |
| jidecards 原生选择题 | 首版不自动套用两档；现有自动判分语义独立，后续另立设计 |

增强智能版可验证 ArkWeb 复用现有 HTML、媒体拦截和公式链，但不得把部分 Web API 的设备标签等同于完整卡片兼容。JS 类 Web 范式不是完整浏览器。轻量基础版不为追求兼容强行打包原生 Anki Core 或整套手机 UI。

当前队首不支持时保持调度不变，提示转手机；不自动埋藏/暂停、不声称完成、也不自建队列跳过。手机接管后按协议失效旧题面，结束或重新建立手表会话。

## 8. 分阶段实施及验收门

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 平台与能力验证 | 候选型号矩阵；JS/FA 与 ArkTS 最小验证；官方 API/分发核对；接入材料清单 | 至少轻量表、智能表各一条真实通信链可行；5.0 明确支持/不支持/待验证；选定最少维护成本路线 |
| P1 基础交互 | 手机连接入口、手表四类页面、两档评分状态机、协议夹具 | 两种客户端对同一夹具显示和消息语义一致；模拟测试不冒充设备通过 |
| P2 真实 Anki 闭环 | 一张卡取卡/翻面/评分/确认/下一张；持久化恢复及跨入口互斥 | Again/Good 和现有手机行为一致；重复、丢包、并发及崩溃窗口得到可信结果 |
| P3 内容与体验 | 文本/图片白名单、长内容、字号、缓存清理、表冠增强 | 问题卡片不误显示或错误评分；圆/方屏可操作；记录包体积、延迟、内存及功耗 |
| P4 扩大兼容与分发 | 按型号/地区/固件的实测表、对应签名产物、商店材料 | 每个宣称支持的组合完成设备验收；未验证设备不写成已支持 |

P0 的可行性发现可能调整客户端数量，不改变两档评分与手机权威调度。平台能力受阻时先给出具体型号证据和可替代路径，不用无限保活或自写调度规避。

## 9. 验证与交接

实施时增加直接行为测试：协议版本/未知消息/精度、UTF-8 字节限额、乱序重复、媒体完整性、评分映射、过期令牌、集合占用、停止会话、重启恢复、日切、手机编辑/同步、未支持内容。

真实 Core 测试核对两档评分后的卡片与复习记录；集成测试针对写前、写中、写后/确认前故障注入。设备验收包含配对、授权拒绝、两端未启动、手机锁屏/被回收、手表熄屏、断连重连、多设备选择、资源缺失及存储不足。不得用模拟器证明 Wear Engine 真机互通。

本次仅新增设计文档与决策索引：按仓库规则运行 `npm run impact -- --json --paths docs/decisions/2026-09-25-wearable-design.md docs/decisions/README.md` 与 `npm run verify -- repo`。这些检查不能证明设计功能已经实现。

后续源码实施按 [验证说明](../development/verification.md) 执行领域测试、全部测试、相关 Core 测试及真实 HAP 构建。轻量工程确认工具链后补充独立可执行构建入口及文档导航，不能预设当前手机构建脚本已能编译它。真机只覆盖安装，保留现有包名/签名身份和用户数据。

首次接手从 P0 开始：确认代表设备、旧版 SDK 与当前接入状态，补齐轻量通信官方正文及接口签名，验证两端最小收发，形成选型记录，然后实现 P1/P2。
