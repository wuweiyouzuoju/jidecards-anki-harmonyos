# 上一阶段记录：标记冲突保持设备中立与 Anki 兼容

状态：已被[当前 JideCards 优先兜底决策](2026-10-03-marking-sync-priority.md)取代。以下保留撤回阶段的事实与目标，不发出当前实施指令。用户后来选择先调查社区，若没有可采用的修复则 JideCards 优先；最新调查和实现以当前决策及源码对照文档为准。

## 实际协议

锁定 Anki 26.05 的卡片和笔记增量合并，在本地记录仍待同步时接受严格更新的远端记录；没有客户端或设备优先级。同 ID 的卡片／笔记以记录为单位选择，不能声称逐个字段或标签自动合并。未改同一记录的变更通常可合并；复习日志可并存。同卡复习的最终状态及需全量覆盖的结构冲突见[官方说明](https://docs.ankiweb.net/syncing.html#conflicts)。

源码：[锁定 chunk 合并](https://github.com/ankitects/anki/blob/26.05/rslib/src/sync/collection/chunks.rs)、[锁定旗标写入](https://github.com/ankitects/anki/blob/26.05/rslib/src/card/mod.rs)。SetFlag 为保留队列不更新卡片 mtime；USN 用于找待同步变化，不能据此还原两次离线旗标操作的真实先后。相同 mtime 时原规则没有能保证各端最终一致的标记决胜规则；本机 HTTP 回归可复现这一缺口。

## 已执行的纠正

- 删除本地标记优先、上传时人为增大剩余卡片／笔记 mtime 的 Core 补丁；撤回生产 opt-in 工厂、构建登记及补丁测试夹具。旗标／星标界面和标准 RPC 对接保留。
- 不修改另一端 AnkiDroid 或服务端，也不建立与客户端品牌绑定的私有同步语义。生产使用原锁定 Core。
- 真实 HTTP 测试的两个 peer 和服务端都使用相同原版 Core；既可代表两个 JideCards，也可代表两个 AnkiDroid。正常双向、较新远端记录选择、字段／调度／高位保留及队列／答题／撤销属于正向回归。
- 两种同步顺序的相同 mtime 旗标一致性仍是默认执行的验收要求，未 ignored，实际失败必须报告。不能用“保持上游行为”声称“跨设备始终同步一致”已经完成。

## 设计约束与未完成范围

正确目标是：无冲突的变更可合并；同一卡片旗标或同一笔记星标的真实冲突，按可比较的实际修订选择一个值；修订相同也须有所有参与端一致接受的确定规则。星标不能用简单并集，否则取消星标无法传播；单卡旗标不能把颜色编号按位 OR。

该目标不是现有原版协议已经实现的保证。要修复原版 AnkiDroid 之间的缺口，需在共同 Core／协议中完成修订记录、同版本决胜及接受规则，或在原协议可表达范围内证明兼容修复。只改 JideCards，无法改变两台未修改 AnkiDroid 的执行行为；也不能假造修改时间把同步顺序变成编辑顺序。

当前并发一致性要求仍未满足。验收：`cargo test -p jidecards_core --features anki-core --locked --test card_marking`；实际结果见[源码对照与验证](../development/flags-marking-audit-2026-10-03.md)。不安装设备，不访问用户集合或真实账户。
